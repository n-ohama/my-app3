# GET_UNCHIN_INFO 設計書

## 位置づけ

`GET_UNCHIN_INFO` は `PA_SOKO` プロシージャの内部プロシージャ。

`PA_SOKO` は受注明細のうち、商品マスタの倉庫コードが `99`（＝倉庫未確定）になっている商品について、実際の出荷倉庫を確定するロジックを持つ。`PA_SOKO` は該当県の優先倉庫候補4件を `YUSEM_DERIVED`（県コードごとに `YUSEM_SOKO1〜4` を持つ倉庫優先順位マスタ）から取得済みで、`WK_YSOKO(1..4).SOKOCD` に保持している。

優先倉庫候補：
- 倉庫コード 11：春日井倉庫（愛知）
- 倉庫コード 16：福岡倉庫（福岡）
- 倉庫コード 41：市川倉庫（千葉）
- 倉庫コード 44：流山倉庫（千葉）

`GET_UNCHIN_INFO` の目的は、梱包箱のサイズが判明した場合に運賃マスタ `UNCMS` から4候補倉庫それぞれの運賃を求め、**運賃が安い順に `WK_YSOKO` を並べ替える**こと。これが本プロシージャの唯一の出力（`WK_YSOKO` はパッケージ変数であり、in-placeで更新する）。

## 前提（呼び出し元が用意するもの）

- `TBL_SKUMS`：処理対象の受注明細（`SKUMS%ROWTYPE` の配列）。パッケージ変数。`PA_SOKO` が事前にセットする。
- `WK_YSOKO(1..4).SOKOCD`：優先倉庫候補4件。パッケージ変数。`PA_SOKO` が `YUSEM_DERIVED` から事前にセットする。

## 引数

- `P_KENCD`：県コード。運賃マスタ `UNCMS` の検索キーとして使用する（送り先の県によって運賃が変わるため）。

## 商品マスタ（SKUMS）の関連カラム

| カラム | 意味 |
|---|---|
| `SKUMS_HINCD` | 商品コード |
| `SKUMS_SUU` | 数量 |
| `SKUMS_KOGUTI` | 個口係数（0〜1）。1個口＝満箱を1として、そのSKU1個が箱をどれだけ占めるかの割合。0.5なら半分を占める。 |
| `SKUMS_JIKAFLG` | 直貼りフラグ。1の場合、商品自体の箱をそのまま出荷箱として使う（伝票を直接貼る）＝箱サイズが商品マスタから既知。 |
| `SKUMS_KONKB` | 梱包区分（1／2／3）。3の場合のみ `KPSIZE` も分類キーに使う。 |
| `SKUMS_HAISOBKB` | 配送便区分。箱をまとめる単位。運賃マスタ `UNCMS` の検索キーにもなる。 |
| `SKUMS_KPSIZE` | 梱包サイズ。`KONKB=3` のときのみ参照する分類キー。 |
| `SKUMS_KPSIZEH`／`T`／`Y` | 商品自体の梱包寸法（縦・横・高さ、mm）。`JIKAFLG=1` のときの箱サイズ算出に使用。 |

## 処理フロー

### 1. 明細の分類

`TBL_SKUMS` の各行を、個口係数によって振り分ける。

- **`KOGUTI < 1`（1個で満箱にならない商品）**
  `KONKB` ＋ `HAISOBKB`（`KONKB=3` の場合はさらに `KPSIZE`）でグルーピングし、同一グループの明細を `TBL_SIZE_PENDING` に積む（商品コード・数量・個口係数を保持）。
- **`KOGUTI = 1`（1個で満箱になる商品）**
  - `JIKAFLG = 1`：箱サイズが自明なので `TBL_SIZE_KNOWN` に積む。サイズは `HAKO_SIZE = (KPSIZEH + KPSIZET + KPSIZEY) / 10`（三辺合計、mm→cm換算）。倉庫によらず一意に決まる。
  - `JIKAFLG ≠ 1`：`TBL_SIZE_PENDING` に積む（上と同じグルーピング規則）。
- **`KOGUTI > 1`（想定外データ）**
  この時点で運賃計算を諦め、`WK_YSOKO` を変更せずに処理を終了する（初期順序のまま）。

### 2. `TBL_SIZE_PENDING` グループの成立チェック

各分類グループについて、グループ内の `個口係数 × 数量` の合計を計算する。

- **合計 > 1**：このグループは1箱に収まらない・箱詰めシミュレーションの対象外と判断し、運賃計算自体を行わず `WK_YSOKO` を変更せずに処理を終了する。
- **合計 ≦ 1**：次のステップ（`HAKOSMS` による箱サイズ算出）に進む。

### 3. 箱サイズ・運賃の算出

4候補倉庫それぞれについて、以下を合算して合計運賃（`TBL_UNCHIN(i).AMOUNT`）を求める。

- **`TBL_SIZE_KNOWN` の各グループ**：`HAKO_SIZE` は倉庫によらず共通。`GET_UNCHIN_PRICE(HAISOBKB, 倉庫コード, HAKO_SIZE)` で `UNCMS` から運賃を引き、加算する。
- **`TBL_SIZE_PENDING` の各グループ**：グループ内の商品を商品コード昇順に `商品コード＋数量＋商品コード＋数量...` で連結した `HAKOKEY` を組み立て、`HAKOSMS` から `(HAKOKEY, 倉庫コード)` で箱サイズを取得する（**倉庫ごとにサイズが変わりうる**。複数件ヒットしても同一サイズなので`ROWNUM=1`で1件に絞る）。得られたサイズで`GET_UNCHIN_PRICE`を呼び、加算する。
- 箱サイズ・運賃のいずれかが1件も取得できない場合は、その時点で `WK_YSOKO` を変更せず処理を終了する。

### 4. 並べ替え

4候補倉庫の合計運賃を昇順ソートし、その順序で `WK_YSOKO(1..4).SOKOCD` を上書きする。**運賃が同額の場合は、元の `YUSEM_DERIVED` 優先順位（`RANK`）が高い方を優先する。**

## 関連マスタ

- **`YUSEM_DERIVED`**：県コードごとの優先倉庫マスタ（`YUSEM_SOKO1〜4`）。`GET_UNCHIN_INFO` の呼び出し前に `PA_SOKO` が参照済み。
- **`HAKOSMS`**：`HAKOKEY`（商品コード＋数量の組み合わせ）と `SOKOCD`（倉庫コード）で箱サイズを引くマスタ。サイズは `HAKO_KPSIZEH` / `HAKO_KPSIZET` / `HAKO_KPSIZEY` の三辺合計をcm換算して求める。
- **`UNCMS`（運賃マスタ）**：`UNCMS_KENCD`・`UNCMS_HAISOBKB`・`UNCMS_SOKOCD`・`UNCMS_KPSIZE` で検索し、指定サイズ以上で最小の `UNCMS_KPSIZE` 区分の運賃（`UNCMS_AMOUNT`）を1件取得する。
